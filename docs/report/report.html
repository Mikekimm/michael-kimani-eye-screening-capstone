2. Technical functionality

Workflow. The clinic app (app.py) takes a pseudonymous patient code, the eye and a fundus image. ScreeningWorkflow runs ScreeningService (decode → quality check → model → decision) and saves the result in SQLite before anything else. SyncService later pushes pending records to the REST backend and pulls specialist reviews. The specialist portal (specialist_app.py) lists flagged and borderline cases with the image, eye and model version, and records approve / override / ungradable decisions as an append-only history.

Key algorithms and technical solutions

  • Train/serve parity. Training resized with nearest-neighbour; the first app used PIL's default. ImagePreprocessor now matches training (a silent source of error found by review).
  • Quality check. Variance of the 4-neighbour Laplacian (sharpness), mean brightness, contrast, and a centre-versus-corner "vignette gap" (fundus photos are circular). Blank or tiny images block screening; blur, darkness or non-fundus appearance only warn, because these heuristics can be wrong.
  • Sensitivity-targeted threshold, O(n log n). Sort positive scores, count positives above each candidate with a binary search, and take the highest threshold whose sensitivity meets the target (keeps specificity as high as possible). Verified against brute force.
  • Borderline band. Scores within 0.10 below the threshold are queued for a specialist instead of cleared.
  • Honest evaluation. Stratified tune/test split (threshold chosen on one half, metrics reported on the other), rank-based AUC with average ranks for ties (matches scikit-learn), and percentile bootstrap 95% intervals.
  • Reliable sync. Idempotent upload by UUID with an image SHA-256; idempotent review import by remote id and a cursor; an unreachable server or a bad token stops the cycle after one attempt; a rejected record is marked failed without blocking the queue.
  • Security basics. Constant-time token comparison, role checks per endpoint, reviewer identity taken from the token, request-size limit (413), strict input validation, errors that do not leak internals.

The original 180-line app.py (UI, model loading, preprocessing and inference in one script) was refactored into a package of 15 modules (about 1,570 lines in src/) plus two thin UI files. Principles applied:

Single responsibility / separation of concernsOne class per job: ImagePreprocessor, ImageQualityChecker, ScreeningService, ScreeningRepository, SyncService; UI files contain presentation only

Dependency inversion / testabilityScreeningService and SyncService receive abstractions, so tests inject a stub classifier and a fake remote
Inheritance and reuseApiClient (transport, auth, error translation) → ClinicClient, SpecialistClient; the same repository class serves the device and the server
Encapsulation, immutabilityFrozen dataclasses for results and records; private connection handling in the repository; enums for laterality, decisions and roles
Error handlingDomain exceptions (InvalidImageError, ImageQualityError, RemoteUnavailableError, ...) so each caller reacts precisely; TensorFlow imported lazily so most code runs without it

6. Limitations and conclusion

The prototype is preliminary screening support, not a diagnosis, and is not clinically validated. Data are retrospective and public, with no patient identifiers, so reported performance is an optimistic in-distribution estimate; no external evaluation or usability study was done; security is prototype-grade; only DR is covered and the client is not an Android app. What the project does show is a tested, offline-first architecture in which screening never depends on the network, no data is lost when connectivity fails, specialist decisions return with a full history, and every claim about the model is separated from the software tests and qualified by its limits. Future work: glaucoma and cataract, packaging the TFLite model in an Android app, an external dataset, and a usability study.
