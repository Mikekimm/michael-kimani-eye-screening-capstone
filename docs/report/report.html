Scope of claims. This is screening and referral support, not a diagnostic device. The models were trained and evaluated only on public datasets; there has been no field deployment, external validation or clinical validation. Every figure below comes from a recorded run in the repository.

1. Scope alignment and feature validation

The approved proposal planned an offline-first Android app that screens fundus photos for diabetic retinopathy (DR), glaucoma and cataract on the device, refers uncertain or high-risk cases to a specialist dashboard, and syncs when connectivity returns. Following supervisor feedback (a feasible prototype with one demonstrable workflow; reconcile offline use with sync and authentication; separate research evaluation from development), effort went first into one complete, tested workflow; the model registry then made adding the glaucoma and cataract models a data task with no code change. The platform changed from React Native with on-device TensorFlow Lite to an installable PWA with server-side inference (one code base for Android and iPhone, models verified and replaced on the server); offline therefore covers capture and queueing, and scoring happens after sync. 2. Technical functionality

Frontend. A React 18 + TypeScript (strict) PWA, mobile-first (bottom tabs below 1024 px, sidebar above). Pages read server data only through hooks that call one typed API client, which attaches the JWT, refreshes it once on a 401 for all concurrent requests, and converts failures into plain-language messages. Health workers register patients by clinic code, choose the eye, and capture a photo with a circular guide (rear camera or gallery); on-device hints flag dark or blurry photos before upload.

Backend. FastAPI with a layered design: routers (HTTP and role guards) → services (use cases) → repositories (all SQL). POST /api/screenings checks type, size and that the bytes really decode as JPEG/PNG, applies the quality gate (blank or tiny images return 422 with a reason), then runs every model the registry has verified and maps each score through that condition's risk policy. One diagnosis_results row is stored per condition with its model version, including "not available" rows, so history shows exactly what ran. Positive or borderline results open a referral with a review target (urgent 24 h, routine 72 h; a configurable design decision, since the proposal sets no limit); overdue cases rise to the top of the specialist queue. Specialists approve, override any scored condition (reason required), request a retake or comment; each action is appended to review_events, which the ORM refuses to update or delete, and reaches the health worker on the next sync. Each result card shows the model's measured limits; results made by an earlier model are never re-scored and carry a notice instead.

Offline and sync. Without a connection, photos and new patients are stored in IndexedDB with a client-generated UUID. A sync engine pushes them in order (patients first), retrying with bounded exponential backoff and full jitter; because the server is idempotent on the UUID, a retry after a lost reply returns the original record rather than a duplicate. Each cycle then pulls specialist decisions made since the last pull. Offline mode captures and queues; it does not run the model on the device.

Data handling and privacy. SQLite by default, PostgreSQL by configuration, schema managed by Alembic migrations. Patients are pseudonymous codes; images are stored under random names and served only to authorised users; analytics and audit records contain no images or patient fields; secrets live only in a git-ignored .env generated by a script.

Different inputs: negative, borderline and positive scores, real and synthetic fundus photos, blank, tiny, corrupt, mislabelled, oversized and future-dated uploads, name-like patient codes, free-text facilities, weak passwords, expired and replayed tokens, and every role against every route. Improvements made because of testing: a form test exposed that the password field dropped its form reference, so sign-in could never succeed (fixed with forwardRef); an end-to-end script test exposed that the calibration script did not write its outputs (fixed); screenshots led to listing DR first and to plain-language referral reasons; Lighthouse raised SEO from 91 to 100; axe-core found unlabeled camera inputs and, after the new models, low-contrast amber badges (both fixed); the parity test showed the app was resizing every photo with nearest-neighbour, which would have changed 6 of 24 DR v2 decisions, so each model card now states its resize.

Analysis: inference is a small share of the round trip, and limiting it to one thread costs about 5 ms, so a modest server CPU is sufficient. On a slow phone and network the wait rises to about 3 s, dominated by the upload; the offline queue means the worker can continue with the next patient meanwhile. Low-end figures are emulated (Chrome DevTools); physical low-end devices and real iOS Safari have not been tested.

DR v2 is MobileNetV2 fine-tuned from block_13_expand on the Kaggle EyePACS + APTOS + Messidor redistribution, split 70/15/15 by image group; the threshold was chosen on validation (highest with sensitivity ≥ 85%) and the test split scored once. Its figures are a held-out test split by image (no patient IDs available; near-duplicates could not be excluded); not external validation; not clinically validated: the notebook found as many groups as images, so augmented copies may sit in both training and test. Every figure was recomputed from the notebook's predictions with the app's own threshold and bootstrap code and matched; the served file has the notebook's checksum, and on 24 of its test photos the app reproduces the notebook's scores within 0.021 (tolerance 0.03, my choice) with no decision changed. Glaucoma and cataract (ODIR-5K) were split by patient; ODIR labels come from free-text keywords and its positive classes are small. For reference only, Gulshan et al. (2016) reported 90.3% / 98.1% on different data and a high-specificity operating point; our referable-DR (grade 2+) sensitivity is 0.869. The earlier DR model (v0.3) reached only 0.542 sensitivity on its validation fold.

  • Specificity below target means about 25% of eyes without DR are referred, and about 9 in 10 glaucoma flags are false alarms; the result screens say so next to each result, and a specialist reviews every referral.
  • Not done: on-device inference in the browser, a load balancer, a usability study with health workers (SUS kit ready), tests on a physical phone (planned on an iPhone 13 Pro after the HTTPS deploy), external validation and smartphone-lens images.
