Scope of claims. This is screening and referral support, not a diagnostic device. The model was trained and evaluated only on public datasets; there has been no field deployment or clinical validation. Every figure below comes from a recorded run in the repository.

1. Scope alignment and feature validation

The approved proposal planned an offline-first Android app that screens fundus photos for diabetic retinopathy (DR), glaucoma and cataract on the device, refers uncertain or high-risk cases to a specialist dashboard, and syncs when connectivity returns. Following supervisor feedback (a feasible prototype with one demonstrable workflow; reconcile offline use with sync and authentication; separate research evaluation from development), effort went into one complete, tested DR workflow, while keeping the multi-disease design real: glaucoma and cataract are registered conditions that report "Model not available yet" until a trained model is added, which needs no code change. Added beyond the proposal: authentication with role-based access (Argon2, JWT refresh rotation, login throttling), an image quality gate, a SHA-256-verified model registry with model cards, eye laterality and model version on every result, an append-only review log and an audit log (the last three answer the supervisor's data-model corrections).

2. Technical functionality

Frontend. A React 18 + TypeScript (strict) PWA, mobile-first (bottom tabs below 1024 px, sidebar above). Pages read server data only through hooks that call one typed API client, which attaches the JWT, refreshes it once on a 401 for all concurrent requests, and converts failures into plain-language messages. Health workers register patients by clinic code, choose the eye, and capture a photo with a circular guide (rear camera or gallery); on-device hints flag dark or blurry photos before upload.

Backend. FastAPI with a layered design: routers (HTTP and role guards) → services (use cases) → repositories (all SQL). POST /api/screenings checks type, size and that the bytes really decode as JPEG/PNG, applies the quality gate (blank or tiny images return 422 with a reason), then runs every model the registry has verified and maps each score through that condition's risk policy. One diagnosis_results row is stored per condition with its model version, including "not available" rows, so history shows exactly what ran. Positive or borderline results open a referral; specialists approve, override (reason required), request a retake or comment, and each action is appended to review_events, which the ORM refuses to update or delete.

Offline and sync. Without a connection, photos and new patients are stored in IndexedDB with a client-generated UUID. A sync engine pushes them in order (patients first), retrying with bounded exponential backoff and full jitter; because the server is idempotent on the UUID, a retry after a lost reply returns the original record rather than a duplicate. Each cycle then pulls specialist decisions made since the last pull. Offline mode captures and queues; it does not run the model on the device.

Data handling and privacy. SQLite by default, PostgreSQL by configuration, schema managed by Alembic migrations. Patients are pseudonymous codes; images are stored under random names and served only to authorised users; analytics and audit records contain no images or patient fields; secrets live only in a git-ignored .env generated by a script.

Analysis: inference is a small share of the round trip, and limiting it to one thread costs about 5 ms, so a modest server CPU is sufficient. On a slow phone and network the wait rises to about 3 s, dominated by the upload; the offline queue means the worker can continue with the next patient meanwhile. Low-end figures are emulated (Chrome DevTools); physical low-end devices and real iOS Safari have not been tested.

6. Model evaluation, limitations and next steps

The DR model is MobileNetV2 (frozen ImageNet backbone, small head) trained for 8 epochs on the Kaggle EyePACS + APTOS + Messidor redistribution with a group-aware 5-fold split. The training notebook reported, on its 47,234-image validation fold at threshold 0.5: accuracy 0.790, precision 0.920, recall 0.542, F1 0.682. A hold-out notebook re-creates that fold, verifies it, and checks that the shipped files reproduce those numbers before any metric is attributed to the deployed model. Held-out results for the shipped model: pending; until then the app, model card and README state "metrics not yet measured". At threshold 0.5 the notebook's recall (0.542) is well below the 85% sensitivity target, which is why the threshold is recalibrated for sensitivity, at the cost of more referrals.

  • Evaluation is image-level (no patient IDs), the redistribution contains augmented near-duplicates, and the validation fold also guided early stopping, so results are optimistic; there is no external test set and no smartphone-lens images.
  • Glaucoma and cataract need trained models (e.g. ODIR-5K). Offline inference in the browser, PostgreSQL/Docker runs, a usability study with health workers and tests on physical low-end devices remain to be done.
  • The TFLite export is quantized and differs from the Keras model by up to 0.034 in score on test inputs; the full-fold difference will be recorded by the hold-out run.
